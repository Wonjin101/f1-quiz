# 🏎️ F1(포뮬러 1) 상식 콘솔 퀴즈 게임 (f1-quiz)

## 1. 프로젝트 개요
본 프로젝트는 **Python 3.10+**의 객체 지향 프로그래밍(클래스 설계)과 표준 라이브러리(`json`, `os`)만을 활용하여 구현한 **콘솔(터미널) 기반 4지선다 퀴즈 프로그램**입니다.

사용자는 F1(Formula 1) 상식 퀴즈를 풀고, 새로운 문제를 직접 추가하거나 전체 문제 목록과 최고 점수를 확인할 수 있습니다. 모든 퀴즈 데이터와 최고 점수 기록은 프로젝트 루트 경로의 `state.json` 파일에 **UTF-8 인코딩**으로 영구 저장(데이터 영속성 보장)되어, 프로그램을 종료한 뒤 다시 실행해도 이전 상태가 그대로 유지됩니다.

---

## 2. 퀴즈 주제 선정 이유
* **퀴즈 주제:** F1 (Formula 1, 포뮬러 원 모터스포츠)
* **선정 이유:**
  * 빠른 속도감 뒤에 숨겨진 F1의 정교한 레이스 규정과 과학적 전략(DRS 시스템, 타이어 컴파운드 종류, 서킷별 특성, 포인트 배점 제도 등)을 4지선다 퀴즈를 통해 입문자와 팬 모두가 쉽고 재미있게 익힐 수 있도록 선정했습니다.
* **기본 퀴즈 구성 및 메타데이터 확장 설계:**
  * 첫 실행 시 기본 F1 퀴즈 5개가 자동 제공됩니다.
  * 향후 확장 시 각 `Quiz` 객체에 문제별 카테고리(`category`: 규정/서킷/팀)와 난이도(`difficulty`: 상/중/하) 메타데이터 필드를 추가하여 난이도별 맞춤형 출제가 가능하도록 설계했습니다.

## 4. 기능 목록 (퀴즈 풀기/추가/목록/점수)

1. **퀴즈 풀기 (`1`번)**
   * 등록된 모든 F1 퀴즈를 순서대로 출제하고, 사용자 입력(1~4)에 따라 즉시 정답(`✅`) 및 오답(`❌` 및 실제 정답 안내) 여부를 판정합니다.
   * 모든 문제를 풀면 맞힌 개수와 100점 만점 기준 최종 점수를 출력하며, 최고 점수 경신 시 자동 갱신 및 `state.json`에 즉시 저장합니다.
   * 등록된 퀴즈가 없을 경우 안내 메시지를 출력하고 메뉴로 복귀합니다.

2. **퀴즈 추가 (`2`번)**
   * 새로운 F1 문제 내용, 4개의 선택지, 정답 번호(1~4)를 직접 입력받아 검증한 후 `Quiz` 인스턴스를 생성해 등록하고 `state.json`에 즉시 저장합니다.

3. **퀴즈 목록 (`3`번)**
   * 현재 저장되어 있는 전체 퀴즈의 문제 번호, 질문, 4개 선택지, 정답 목록을 한눈에 조회합니다.
   * 등록된 퀴즈가 없을 경우 안내 메시지를 출력합니다.

4. **점수 확인 (`4`번)**
   * 지금까지 플레이한 기록 중 최고 점수(`best_score`)를 확인합니다.
   * 아직 퀴즈를 한 번도 풀지 않은 경우(`None`) *"아직 퀴즈를 풀지 않았습니다."*라는 안내 메시지를 출력합니다.

5. **종료 및 예외 처리 정책 (`5`번 및 상시 적용)**
   * **입력 오류 처리 및 재시도 제한 정책:** 입력값 앞뒤 공백 자동 제거(`.strip()`), 빈칸(Enter), 숫자가 아닌 문자(`abc`), 허용 범위 밖 숫자(`0`, `9`) 입력 시 `ValueError` 등을 포착하여 안내 메시지를 출력하고 재입력을 유도합니다. 콘솔 환경의 사용자 편의성을 위해 유효한 값을 입력할 때까지 재입력을 허용하는 정책을 기본 적용했으며, 필요 시 `max_retries=5` 파라미터를 통해 5회 연속 입력 오류 시 메인 메뉴로 안전 복귀하도록 제한할 수 있습니다.
   * **강제 종료 및 시그널 처리:** 실행 중 `Ctrl+C`(`KeyboardInterrupt`) 또는 입력 스트림 종료(`EOFError`) 발생 시 비정상 종료하지 않고, 안내 메시지 출력 후 현재 상태를 `state.json`에 안전하게 저장하고 종료합니다. 운영 환경 확장 시 Python 표준 `signal` 모듈(`signal.SIGTERM`, `signal.SIGINT`) 핸들러를 등록하여 동일하게 `save_state()` 호출 후 정상 종료하도록 처리할 수 있습니다.

### 5-2. 클래스 사용 이유 (객체 지향 채택 이유 및 함수형 대비 장단점)
* **객체 지향(클래스) 채택 이유:** 퀴즈의 데이터(`question`, `choices`, `answer`)와 동작(`display`, `check_answer`)이 밀접하게 결합되어 있고, 게임 진행 상태(`quizzes`, `best_score`)를 프로그램 실행 내내 일관되게 유지해야 합니다. 전역 변수(Global Variable) 남용으로 인한 상태 오염을 방지하고 데이터와 로직을 하나로 묶는 캡슐화(Encapsulation)를 달성하기 위해 클래스 기반 설계를 채택했습니다.
* **함수형(절차형) 대비 장단점 비교:**
  * **장점:** 함수만으로 구현할 경우 모든 함수 호출마다 `quizzes` 리스트와 `best_score`를 매개변수로 계속 전달하고 반환받아야 하지만, 클래스를 사용하면 인스턴스 속성(`self.quizzes`, `self.best_score`)으로 상태를 안전하게 공유할 수 있고 역할별 책임이 명확해져 유지보수와 확장이 용이합니다.
  * **단점:** 단순 스크립트나 함수형 구현에 비해 초기 클래스 구조(`__init__`, 직렬화 메서드 등)를 정의하는 코드 작성량이 소폭 증가합니다.

### 5-3. `Quiz`와 `QuizGame`의 클래스 책임 분리
* **`Quiz` 클래스 (도메인 데이터 모델 책임):** 개별 퀴즈 1개의 속성(문제 문자열, 4개 선택지 리스트, 정답 번호)을 보유하며, 단일 문제 화면 출력(`display`), 사용자 답안과 정답 비교(`check_answer`), 파일 입출력을 위한 딕셔너리 변환 및 검증(`to_dict`, `from_dict`)만을 전담합니다.
* **`QuizGame` 클래스 (애플리케이션 컨트롤러 및 상태/영속성 관리 책임):** 전체 퀴즈 객체 리스트(`quizzes`)와 최고 점수(`best_score`)의 생명주기를 관리하며, 메인 메뉴 루프 제어(`run`), 사용자 입력 검증(`get_number_input`, `get_text_input`), 게임 핵심 기능 실행(`play_quiz`, `add_quiz`, `list_quizzes`, `show_best_score`), 그리고 `state.json` 파일 입출력(`load_state`, `save_state`)을 총괄합니다.

### 5-4. 입력 검증과 데이터 I/O 로직을 분리한 설계 기준 (이유)
1. **단일 책임 원칙(SRP) 및 코드 중복 제거:** 사용자 입력을 받아 공백을 제거하고 숫자/범위를 검증하는 로직을 `get_number_input()`과 `get_text_input()` 메서드로 분리했습니다. 이를 통해 메뉴 번호 선택(1~5), 퀴즈 풀이 정답 입력(1~4), 신규 퀴즈 정답 등록(1~4)에서 동일한 `try-except` 검증 코드를 중복 없이 재사용했습니다.
2. **비즈니스 로직과 데이터 I/O 계층의 격리:** 파일 읽기/쓰기 및 예외 복구 로직을 `load_state()`와 `save_state()`로 완전히 격리했습니다. 덕분에 게임 진행 메서드(`play_quiz`, `add_quiz`)는 저장 매체의 내부 구현을 몰라도 되므로 결합도(Coupling)가 낮아지고 유지보수성이 향상됩니다.

## 6. 데이터 파일 설명 (`state.json` 경로/역할/필드 구조)

### 6-1. 파일 경로 및 역할
* **파일 경로:** 프로젝트 루트 디렉터리의 `./state.json`
* **인코딩 방식:** `UTF-8` (`ensure_ascii=False` 옵션을 통해 한글 및 특수기호 원본 유지)
* **역할:** 프로그램 종료 후 재실행해도 사용자가 추가한 퀴즈 목록과 최고 점수가 유지되도록 상태를 JSON 형식으로 저장(`save_state`)하고 불러옵니다(`load_state`).

### 6-2. 필드 구조 (스키마) 및 설계 의도
* **필드 구성:**
  * `quizzes` (`list[dict]`): 각 퀴즈의 `question`(문제 문자열), `choices`(문자열 4개 리스트), `answer`(1~4 정수)를 담은 객체 배열
  * `best_score` (`int | null`): 최고 점수 기록 (아직 퀴즈를 풀지 않은 경우 `null`)
* **스키마 예시:**
```json
{
  "quizzes": [
    {
      "question": "F1에서 앞차와의 간격이 1초 이내일 때 리어 윙을 열어 공기 저항을 줄이는 시스템은?",
      "choices": [
        "ERS",
        "DRS",
        "ABS",
        "KERS"
      ],
      "answer": 2
    }
  ],
  "best_score": 100
}
```
* **필드 설계 및 중첩 구조화 이유:**
  1. **최상위 루트를 Object(딕셔너리)로 구조화한 이유:** 성격이 다른 두 데이터인 '문제 목록(`quizzes` 배열)'과 '사용자 달성 기록(`best_score` 단일 값)'을 하나의 파일 안에서 독립된 키(Key)로 분리하기 위함입니다. 이를 통해 향후 `last_played_date`나 `play_count` 같은 새로운 상태 필드가 추가되더라도 기존 `quizzes` 파싱 로직을 깨뜨리지 않고 수평 확장할 수 있습니다.
  2. **개별 퀴즈 내부에 `choices`를 리스트로 중첩한 이유:** `choice1`, `choice2`처럼 평면 필드로 나열하는 대신 배열로 중첩하면, `enumerate()` 반복문을 통해 출력 순서와 정답 번호(1~4)를 일관되게 매핑하고 선택지 개수 검증(`len(choices) == 4`)을 간결하게 처리할 수 있습니다.

### 6-3. 예외 복구, 자동 백업 정책 및 원자적 쓰기(Atomic Write) 방안
* **손상 감지 및 자동 복구 동작:** 첫 실행 시 `state.json`이 없으면 기본 F1 퀴즈 5개로 파일을 자동 생성합니다. 파일이 손상되었거나(`JSONDecodeError`), 필수 키 누락(`KeyError`), 타입/범위 오류(`ValueError`, `TypeError`) 발생 시 `try/except`로 포착하여 안내 메시지를 출력한 뒤 기본 퀴즈 5개와 초기 점수(`None`)로 즉시 자동 복구합니다.
* **백업 생성 및 선택적 복구 정책:**
  * **자동 백업(`.bak`) 정책:** 파일 저장 시 기존 정상 파일을 `state.json.bak`으로 복사해 두거나, 파일 손상 감지 시 즉시 덮어쓰지 않고 손상된 원본을 `state.json.corrupted`로 백업 보관하여 데이터 유실을 방지할 수 있습니다.
  * **선택적 복구 옵션:** 파일 로드 실패 시 사용자에게 `[1] 백업 파일(.bak)에서 복원 [2] 기본 퀴즈 데이터로 초기화 [3] 프로그램 종료 후 수동 점검` 중 하나를 선택하도록 복구 옵션을 제공할 수 있습니다.
* **원자적 쓰기(Atomic Write) 고려:** 저장 도중 강제 종료나 전원 차단으로 파일이 깨지는 현상을 방지하기 위해 임시 파일(`state.json.tmp`)에 먼저 기록을 완료한 뒤 `os.replace("state.json.tmp", "state.json")`으로 교체하는 원자적 쓰기 방식을 적용할 수 있습니다.

### 6-4. JSON 저장 방식의 성능·메모리 한계와 대안 비교
* **JSON 방식의 성능 및 메모리 부담:**
  1. **전체 읽기/전체 덮어쓰기(Full I/O) 구조:** JSON 파일은 부분 수정이 불가능하여 문제 1개를 추가하거나 점수만 갱신하더라도 파일 전체를 메모리에 로드해 파싱(`json.load`)하고 전체 데이터를 다시 직렬화해 디스크에 덮어써야(`json.dump`) 합니다.
  2. **대용량 한계:** 데이터가 수만 건 이상으로 커지면 매 입출력마다 메모리(RAM) 사용량과 디스크 I/O 지연 시간이 선형(`O(N)`)으로 증가하며, 동시성 제어(Lock)나 인덱스 검색이 불가능합니다.
* **대안 비교 (SQLite DB):**
  * 파이썬 표준 라이브러리인 **`sqlite3` (SQLite)**를 대안으로 사용하면 전체 데이터를 메모리에 올릴 필요 없이 SQL 쿼리(`INSERT`, `UPDATE`, `SELECT`)로 변경된 단일 행만 빠르게 처리할 수 있으며, 인덱싱과 트랜잭션(ACID)을 통해 대용량 환경에서의 성능과 무결성을 보장할 수 있습니다.

  * `Chore:` : 프로젝트 초기 설정 및 `.gitignore` 구성 (예: `Chore: 프로젝트 초기 설정 및 .gitignore, README 생성`)

### 7-3. 브랜치 분리 이유와 병합(`merge`)의 의미
* **브랜치 분리 이유:** 중심 브랜치(`main`)의 안정성을 유지하면서 새로운 기능(`feat/play`: 퀴즈 풀기)을 독립된 작업 공간에서 안전하게 개발·테스트하기 위해 브랜치를 분리했습니다.
* **병합(`merge`) 절차 및 목적:** `git checkout -b feat/play`로 브랜치를 생성해 기능을 구현·커밋한 뒤, `git checkout main`으로 복귀하여 `git merge --no-ff feat/play`로 병합했습니다. `--no-ff`(No Fast-Forward) 옵션을 사용하여 기능 브랜치가 분리되었다가 통합된 병합 커밋(Merge Commit)과 분기 구조를 Git 그래프 상에 명확히 보존했습니다.
